# GRC Report Generator — Project Configuration

## Project Overview

A production-grade Governance, Risk & Compliance (GRC) report generator web application.
GRC analysts create custom compliance checklists from ISO 27001, SOC 2, NIST CSF 2.0, PCI DSS, HIPAA, and GDPR frameworks. They assess businesses against these checklists and generate downloadable, editable reports.

## Tech Stack

- **Framework**: Next.js 15 with App Router
- **Language**: TypeScript (strict mode)
- **Styling**: Tailwind CSS 4 — NO default AI aesthetic (see Design System below)
- **UI Primitives**: Radix UI (unstyled) — NOT shadcn defaults
- **State**: Zustand for client state, React Query for server state

- **Auth**: Supabase Auth (email + Google OAuth)
- **PDF Export**: @react-pdf/renderer
- **Testing**: Vitest + React Testing Library + Playwright

## Design System — CRITICAL: No AI Aesthetic

This application is for compliance professionals. The UI must feel like a tool built by a design team at a serious SaaS company, NOT generated by AI.

### Anti-Patterns to AVOID

- Purple-to-blue gradients on white backgrounds
- Inter/Roboto/system fonts everywhere
- Rounded-everything with identical 8px radii
- Generic card grids with drop shadows
- Overuse of emoji as icons
- Cookie-cutter dashboards with identical stat cards
- Gratuitous animations on every element

### Design Direction: "Editorial Utility"

Think: Stripe's documentation meets a Bloomberg terminal meets a law firm's intranet.

**Typography**:
- Headings: "Instrument Serif" (Google Fonts) — adds gravitas and distinction
- Body: "DM Sans" — clean but not generic
- Monospace/IDs: "JetBrains Mono" — for control IDs, code references
- Tight letter-spacing on headings (-0.03em), generous on labels (+0.05em)

**Color Palette**:
```
--ink:          #1B1F23     (primary text — near-black, not pure black)
--ink-muted:    #57606A     (secondary text)
--ink-subtle:   #8B949E     (tertiary, labels)
--surface:      #FFFFFF     (cards, panels)
--surface-alt:  #F6F8FA     (page background, alternating rows)
--surface-inset:#ECEEF1     (inset panels, code blocks)
--border:       #D1D9E0     (default borders — visible but not harsh)
--border-muted: #E8ECEF     (subtle dividers)
--accent:       #0550AE     (primary actions — deep blue, not electric)
--accent-hover: #033D8B     (hover state)
--accent-subtle:#DDE8F8     (selected states, tags)
--success:      #1A7F37     (compliant)
--success-bg:   #DAFBE1
--warning:      #9A6700     (partial compliance)
--warning-bg:   #FFF8C5
--danger:       #CF222E     (non-compliant)
--danger-bg:    #FFEBE9
--neutral:      #6E7781     (not applicable)
--neutral-bg:   #F3F4F6
```

**Layout Principles**:
- Left sidebar navigation (collapsible) — NOT top nav tabs
- Dense data layouts with good whitespace — more "tool" than "marketing site"
- Tables as the primary data display (not card grids) for assessment data
- Borderless cards — use background color shifts and spacing instead
- Asymmetric spacing: 32px left margin on content, 24px right
- No rounded corners above 6px. Buttons: 4px. Cards: 6px. Nothing is a pill.

**Iconography**:
- Lucide icons ONLY (consistent stroke width)
- NO emoji in the UI (only in export reports as optional flourish)
- 16px default icon size, 20px for nav

**Interactions**:
- Only animate what matters: page transitions (150ms fade), dropdown opens, toast notifications
- No hover-lift effects on cards
- Keyboard-first: all actions reachable via keyboard shortcuts
- Focus rings: 2px solid var(--accent), 2px offset

**Component Patterns**:
- Buttons: Solid primary (filled accent), Ghost secondary (no border, subtle bg on hover)
- Inputs: 1px border, 36px height, no rounded pill shapes
- Tables: Alternating row backgrounds, sticky headers, sortable columns
- Modals: Slide from right as drawer panels (not centered popups)
- Status badges: Dot indicator + text, not colored pills
- Breadcrumbs for navigation context, not back buttons

## Database Schema (Prisma)

```prisma
model User {
  id            String       @id @default(cuid())
  email         String       @unique
  name          String?
  avatarUrl     String?
  createdAt     DateTime     @default(now())
  templates     Template[]
  assessments   Assessment[]
}

model Template {
  id            String       @id @default(cuid())
  name          String
  description   String?
  userId        String
  user          User         @relation(fields: [userId], references: [id])
  controls      TemplateControl[]
  assessments   Assessment[]
  createdAt     DateTime     @default(now())
  updatedAt     DateTime     @updatedAt
}

model TemplateControl {
  id            String       @id @default(cuid())
  templateId    String
  template      Template     @relation(fields: [templateId], references: [id], onDelete: Cascade)
  framework     String       // e.g. "iso27001"
  domain        String       // e.g. "A.5 – Organisational Controls"
  controlId     String       // e.g. "5.1"
  controlName   String
  description   String?
  sortOrder     Int          @default(0)

  @@unique([templateId, framework, controlId])
}

model Assessment {
  id            String       @id @default(cuid())
  name          String
  templateId    String
  template      Template     @relation(fields: [templateId], references: [id])
  userId        String
  user          User         @relation(fields: [userId], references: [id])
  status        AssessmentStatus @default(IN_PROGRESS)
  responses     AssessmentResponse[]
  createdAt     DateTime     @default(now())
  updatedAt     DateTime     @updatedAt
}

model AssessmentResponse {
  id            String       @id @default(cuid())
  assessmentId  String
  assessment    Assessment   @relation(fields: [assessmentId], references: [id], onDelete: Cascade)
  framework     String
  controlId     String
  status        ComplianceStatus @default(NOT_ASSESSED)
  notes         String?      @db.Text
  evidence      String?      @db.Text
  updatedAt     DateTime     @updatedAt

  @@unique([assessmentId, framework, controlId])
}

enum AssessmentStatus {
  IN_PROGRESS
  COMPLETED
  ARCHIVED
}

enum ComplianceStatus {
  NOT_ASSESSED
  COMPLIANT
  PARTIALLY_COMPLIANT
  NON_COMPLIANT
  NOT_APPLICABLE
}
```

## Implementation Phases

### Phase 1: Foundation (Priority)
1. Project scaffolding (Next.js 15 + TypeScript + Tailwind)
2. Design system: UI primitives (Button, Input, Table, Drawer, Toast)
3. Sidebar layout with routing
4. Framework data files (ISO 27001, SOC 2, NIST, PCI DSS, HIPAA, GDPR)
5. Database schema + Prisma setup

### Phase 2: Core Features
1. Template Builder — framework picker, control search/filter, multi-select
2. Template CRUD (create, edit, duplicate, delete)
3. Assessment Runner — status toggles, notes, evidence fields per control
4. Auto-save with optimistic updates
5. Assessment progress tracking

### Phase 3: Reports
1. Report view with executive summary
2. Compliance rate visualisation (D3 or Recharts — not pie charts, use horizontal stacked bars)
3. Non-compliant findings highlight section
4. PDF export (@react-pdf/renderer)
5. CSV export
6. HTML export (printable)

### Phase 4: Auth & Polish
1. Supabase Auth integration
2. Protected routes
3. Keyboard shortcuts (Cmd+K command palette, Cmd+S save)
4. Toast notifications
5. Empty states with clear CTAs
6. Loading skeletons (not spinners)
7. Mobile responsive sidebar (collapse to icons)

### Phase 5: Advanced
1. Assessment comparison (diff two assessments)
2. Template marketplace (share templates)
3. Team collaboration (multi-user assessments)
4. Audit log
5. AI-powered gap analysis (Claude API integration)

## Coding Standards

- **Immutability**: Always create new objects. Never mutate state directly.
- **File size**: Max 300 lines per file. Extract components and hooks.
- **Naming**: PascalCase components, camelCase functions/variables, UPPER_SNAKE constants.
- **Exports**: Named exports only. No default exports except page.tsx files.
- **Error handling**: Every async operation wrapped in try/catch. User-facing errors shown via toast.
- **Types**: No `any`. Explicit return types on all functions. Zod for runtime validation.

## Git Workflow

- Conventional commits: `feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `chore:`
- Feature branches: `feat/template-builder`, `fix/assessment-save`
- PRs require: passing tests, no TypeScript errors, code review
- Main branch is always deployable

## Security Rules (Non-Negotiable)

- Never hardcode secrets. Use environment variables.
- Validate ALL user input server-side with Zod.
- Use parameterised queries only (Prisma handles this).
- Sanitise any user content rendered as HTML (report exports).
- CSRF protection on all mutations.
- Rate limiting on API routes.
- Row-level security: users can only access their own data.
